1. Executive Overview

What the project is

Indian Contract Intelligence Agent (ICIA) is a Python 3.12/FastAPI modular monolith for tenant-scoped contract intelligence. It accepts PDF and DOCX contracts, preserves immutable document versions and provenance, indexes their contents, retrieves relevant evidence, produces evidence-backed answers, extracts structured contract facts, flags deterministic product-risk signals, compares analyzed versions, and can retrieve separately versioned legal-corpus evidence through a bounded agent.

The system is not an autonomous legal-advice system. It reports what a contract or authorized source states, exposes evidence, and labels risk as a product classification. It does not decide legality, validity, enforceability, or legal liability.

30-second answer. “I built a production-oriented contract intelligence backend. A user uploads a PDF or DOCX; the system validates and versions it, extracts structured text and provenance, creates hierarchy-aware chunks and 384-dimensional E5 embeddings, and stores them in PostgreSQL with pgvector. Search combines dense vectors with request-scoped BM25 and optional local reranking. Chat is fail-closed: the model receives bounded, tenant-authorized evidence and citations are verified by the application. Separate deterministic services extract clauses, obligations, and risk signals, compare contract versions, and support a bounded contract-plus-legal agent.”
2-minute answer. “The interesting engineering problem is not just calling an LLM. It is preserving trust from upload to answer. Upload validation checks type, signature, size, filename, checksum, and duplicate versions. Processing preserves page, section, clause, block, and extraction-method provenance. Every retrieval request is tenant-scoped before evidence is exposed. Dense retrieval uses pgvector; sparse retrieval preserves legal identifiers and numbers; hybrid search uses reciprocal-rank fusion; an optional cross-encoder reranks only retrieved candidates. Generation gets application-assigned E1-style evidence IDs, a context budget, structured JSON output, and fail-closed citation validation. Contract analysis is mostly deterministic and persists a replaceable derived snapshot keyed by version and configuration hash. Auth uses signed access tokens, scrypt password hashes, and tenant memberships. The main trade-off is a simple modular monolith with synchronous CPU-heavy processing: it is understandable and easy to operate, but needs queues, object storage, distributed metrics, and scaling work for larger traffic.”
5-minute answer structure. Start with the user problem, draw the upload-to-index path, then draw search-to-answer. Explain tenant scope and evidence as the safety boundaries. Add the immutable document/version model, chunks with provenance and vectors, derived analysis/comparison snapshots, and separate legal corpus tables. Close with the current deployment shape, synchronous processing bottleneck, and the next scaling step: durable jobs plus isolated model workers.

Why it is technically interesting

  • It combines transactional data, immutable versioning, vector search, lexical search, reranking, structured extraction, and bounded agent orchestration.
  • It treats provenance, tenant isolation, and citation validation as application invariants rather than prompt instructions.
  • It deliberately keeps contract analysis deterministic where possible and isolates optional LLM semantics from canonical state.
  • It contains realistic operational constraints: local model memory, OCR subprocess bounds, synchronous work, configuration hashing, and incomplete production-scale measurement.

2. Problem, Requirements, and Scope

The problem

Contracts are long, structurally irregular, versioned, and full of high-value details such as notice windows, renewal mechanics, liability caps, obligations, payment terms, and governing-law clauses. Keyword search misses paraphrases; a raw LLM call can hallucinate; a flat text dump loses page and clause provenance; and a multi-tenant product cannot trust caller-supplied tenant identifiers.

Naive approach and why it fails

A naive design stores uploaded text in one table and sends the entire contract to an LLM. It fails on context limits, latency, OCR and page provenance, access isolation, reproducibility, citation trust, duplicate uploads, and version comparison. ICIA answers these by separating immutable sources from derived artifacts, retrieving bounded evidence, validating structured output, and making scope explicit at every boundary.

Scope language for an interview

Do not overclaim. The repository provisions Redis but does not use Redis reads/writes for application caching. It has a legal corpus and legal retrieval, but legal data is separate and not automatically authoritative. The recorded 54-test checkpoint and Compose results are historical documentation; they are not a fresh verification performed for this PDF.

  1. Authentication supplies the authoritative tenant; a body tenant ID is ignored.
  2. The bounded read detects oversize uploads before expensive processing. Extension, MIME, magic bytes, filename safety, emptiness, and checksum are validated.
  3. Storage keys are generated from IDs, not user paths. Same-title identical content is rejected by checksum uniqueness; changed content receives a new version.
  4. PDF native blocks are preferred; low-text/image pages can use Tesseract within a timeout. DOCX uses python-docx; physical pages are not invented when conversion is unavailable.
  5. Indexing preserves sections, clauses, pages, printed labels, extraction method, and source-block provenance. Embeddings are checked for finite values and dimension 384.
  6. Failure marks the version FAILED; the indexing transaction rolls back partial chunk changes.

7. Feature Deep Dives

Document intelligence

What/why: turn messy source files into traceable structured artifacts. Internal decision: structural boundaries take precedence over token boundaries; headings, clause numbers, and provenance survive chunking. Edge cases: corrupt files, MIME/signature mismatch, empty files, OCR timeout, low-text pages, missing printed labels, duplicate checksum, and partial indexing. Interview point: “READY means processing and indexing completed, not merely that bytes were uploaded.”

Retrieval

What/why: dense embeddings capture paraphrase; BM25 preserves exact legal numbers and identifiers; RRF avoids forcing incomparable score scales into one formula. Candidate size is bounded, tenant predicates are applied in SQL first, and tie-breaking is deterministic. Trade-off: BM25 materializes the authorized chunk set per request, which is simple and auditable but a likely scale bottleneck.

Contract extraction and risk

What/why: stable facts and risk signals should not depend on an LLM response. Deterministic extraction is authoritative for identifiers and provenance; semantic classification is optional and narrowly scoped. Evidence IDs and confidence values are validated. Rules include automatic renewal, short cancellation windows (<=30 days), long termination notice (>=90 days), long confidentiality survival (>=5 years), uncapped liability, indemnity, payment, IP, restrictive covenant, missing clause, and deadline signals. These are product-risk findings, not legal conclusions.

Legal retrieval

Legal corpus versions, documents, versions, and chunks use separate tables and L1-style evidence. Corpus-version scope is mandatory. The separation prevents accidental mixing of contract text and legal source text and makes source release identity explicit.

Server-rendered UI

The current product surface is Jinja-rendered: dashboard, contract workspace, upload, search, Ask ICIA, comparison, legal upload, administration, login, signup, and logout. The README's “Next.js later phase” is not current behavior.

Indexes and constraints

PostgreSQL indexes cover tenant IDs, document/version lookups, version-section-clause filters, and HNSW cosine vectors. Uniqueness prevents duplicate versions, chunk identities, analysis configurations, comparisons, corpus releases, and memberships. Foreign keys cascade source deletion to derived rows; parent chunks use SET NULL. JSON stores provenance/metadata and derived payloads where fields evolve as a validated Pydantic contract rather than requiring a column for every extracted fact.

Transactions and concurrency

Indexing deletes/rebuilds a version's chunks transactionally; a failure rolls back and marks the version FAILED. Idempotency is database-backed through unique constraints and configuration hashes. A concurrent duplicate upload or analysis can still race before commit; the unique constraint is the final arbiter and the service must map that conflict. There is no distributed transaction joining local files, PostgreSQL, Groq, and model caches, so recovery is operationally important.

Whiteboard questions

At 10x traffic, inspect BM25 scans, vector index memory, connection pool limits, synchronous ingestion, and JSON snapshot size. At 100x, move processing and embedding to durable jobs, use object storage, separate model workers, aggregate metrics, and consider a dedicated sparse/vector system only after measurements justify the added consistency cost.

10. Caching, Jobs, and State

What actually exists

  • FastEmbed model files are cached locally in a mounted model-cache volume.
  • Embedding reuse is database-backed by content hash and embedding configuration hash.
  • SQLAlchemy uses connection pooling and pool_pre_ping.
  • Redis is created and managed in the resource layer and is provisioned by Compose, but no application cache key is read or written on the request path.
  • No Celery/RQ/Kafka worker, job table, conversation table, durable agent-run table, or distributed cache is implemented.
Interview correction. Do not say “Redis caches retrieval.” The accurate answer is: “Redis is provisioned for future ephemeral infrastructure, but current application semantics do not depend on it; readiness intentionally checks PostgreSQL only.”

Why this matters

The absence of a queue means upload, OCR, parsing, chunking, embedding, and indexing occupy the HTTP request. This is understandable for an early modular monolith and simplifies consistency, but it increases timeout risk and makes horizontal scaling harder when model memory and CPU are involved.

Exact mechanics

Documents use the E5 passage: prefix and queries use query:. Dense scoring is 1 - cosine distance. BM25 uses k1=1.2 and b=0.75, with normalization that preserves legal identifiers, numbers, hyphenated terms, and Devanagari. Hybrid scoring uses:

RRF(d) = sum(weight / (rrf_k + rank)), with default rrf_k=60 and equal weights. Ties use chunk UUIDs for deterministic output.

Why retrieval is a safety boundary

SQL predicates apply tenant/document/version scope before evidence is exposed. The context builder assigns deterministic E1, E2 IDs to the full authorized registry, then selects by item and estimated-token limits. Items excluded from selected context are not citation-authorized. Unknown or duplicate IDs fail; model-supplied metadata is ignored.

LLM behavior

Groq is called with temperature zero, JSON response format, 30-second default timeout, and up to two retries. Missing configuration, timeout, connection/5xx, rate limit, auth, malformed output, and invalid citation cases map to distinct application errors. No sufficient authorized reranked evidence means no LLM call.

Latency includes database retrieval, local embedding/reranking, network LLM time, and retries. CPU reranking reports are experimental and based on small datasets; they should not be presented as production SLA numbers. Hallucination risk is reduced by evidence gates, structured output, and citation validation, but retrieval incompleteness and corpus quality remain risks.

14. Security and Trust Boundaries

Implemented controls

  • HS256 signed access tokens include subject, tenant, issue/expiry, issuer, audience, and access-token type.
  • Passwords use salted hashlib.scrypt; production requires a JWT secret of at least 32 characters and disallows bootstrap configuration.
  • Authenticated context verifies active user, tenant, membership, and role. ADMIN, REVIEWER, and VIEWER permissions are explicit.
  • Caller tenant fields are overwritten by authenticated scope; optional X-Tenant-ID must match the signed claim.
  • Generated storage keys and path resolution resist traversal; uploads and subprocesses are bounded.
  • SQLAlchemy parameters and Pydantic validation reduce injection and malformed-input risks.
  • Retrieved contract text is data, not instructions; the agent exposes typed tools only; evidence/citation checks are application-owned.

Weaknesses to state clearly

No MFA, SSO, refresh-token rotation, email verification, general policy engine, application rate limiter, centralized audit log, or dependency security program is established in the current implementation. Local storage is not object-store replicated. Prompt-injection defense is defense-in-depth, not a claim that malicious text is solved.

20. Model Interview Answers

Question: Why not call an LLM with the whole contract?
Testing: Retrieval, context limits, safety, and provenance.
Answer: “Whole-document prompting is expensive, latency-heavy, and loses control over what supports an answer. I first retrieve authorized chunks, preserve their page and clause provenance, bound the context, and give the model application-assigned evidence IDs. The model proposes wording, but the server verifies citations and metadata. That does not eliminate hallucination, but it makes unsupported citations fail closed.”
Follow-up: “What if retrieval misses the clause?”
Think: Retrieval quality is a separate measurable failure mode; improve chunking, hybrid search, reranking, and evaluation rather than loosening citation rules.
Question: Why PostgreSQL plus pgvector?
Testing: Storage trade-offs and system boundaries.
Answer: “The system needs relational constraints for tenants, versions, memberships, and derived snapshots, but also vector similarity over chunks. pgvector lets us filter by tenant and version in the same database and keeps operational consistency simple. A dedicated vector system could be better at very high vector scale, but then embeddings and metadata need synchronization and another failure path. I would move only after measurements show PostgreSQL is the bottleneck.”
Follow-up: “What is the current vector index?”
Think: HNSW with cosine distance, 384 dimensions, and configured m/ef-construction.
Question: Is Redis the cache?
Testing: Whether the candidate read the implementation.
Answer: “No. Redis is provisioned and its client lifecycle exists, but the current request path does not read or write application cache keys. Model caching is local filesystem caching, and embedding reuse is database-backed. That is an important distinction. Redis can support future rate limits or ephemeral jobs, but readiness deliberately checks PostgreSQL only today.”
Question: How do you prevent cross-tenant data exposure?
Testing: Auth and data-access boundaries.
Answer: “The signed token contains the tenant, and the request context verifies user activity and membership. Route payload tenant IDs are overwritten or ignored. Retrieval applies tenant predicates before evidence is built, and contract/legal services validate version ownership and scope. An optional tenant header must match the signed claim. The remaining improvement would be stronger centralized policy/audit controls and broader negative integration tests.”
Question: What is the first change for 100x traffic?
Testing: Prioritization under constraints.
Answer: “I would measure first, but the obvious pressure point is synchronous ingestion: OCR, parsing, embeddings, and indexing occupy the API process. I would add a durable job state machine and worker pool, move originals to replicated object storage, and make the API return processing status. In parallel I would replace per-request BM25 materialization with a persistent index. I would not start with microservices or sharding without measurements.”

23. One-Page Revision Sheet

ICIA in one page

Purpose: tenant-scoped, evidence-backed contract intelligence for PDF/DOCX documents, with separate legal retrieval.

Architecture: Browser/API -> FastAPI -> auth/validation -> modular services -> PostgreSQL/pgvector + local storage; local E5/reranker; optional Groq; Tesseract/LibreOffice; Redis provisioned but not application cache; Nginx in production.

Key APIs: health, ready, auth token/bootstrap, documents, search, chat, agent/query, contract analyze/read, compare/read, admin, Jinja UI.

Core flow: validate -> version -> parse/OCR -> processed artifact -> structural chunks -> 384-dim E5 embeddings -> HNSW; query -> dense/BM25 -> RRF -> optional rerank -> E1 evidence -> bounded Groq JSON -> citation verification.

Database: tenants/users/memberships; documents/versions; chunks; contract analyses/comparisons; separate legal corpus/document/version/chunks. Immutable source, replaceable derived snapshots, configuration-hash idempotency.

Numbers: 25 MB default upload; chunks target 600, soft 1000, hard 1500 tokens; embedding dimension 384; RRF k 60; reranker candidates 40, default final 5; generation context 6000 estimated tokens; output 1200; Groq timeout 30s, retries 2; risk defaults 30/90/5 days/years.

Main trade-offs: modular monolith is simple but less independently scalable; pgvector is operationally unified but may need separation at scale; local models avoid egress but consume CPU; deterministic extraction is auditable but semantically incomplete; synchronous processing is simple but blocks API capacity.
